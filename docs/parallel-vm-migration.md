# Переход на отдельную VM с сохранением действующей установки

Это предложение миграции на 15 ноября 2026 года. Новая VM, перенос данных
и переключение пользователей ещё не выполнены. Переименование существующего
репозитория в `prairielearn-deployment` не меняет действующую VM и её данные.

Цель — развернуть рядом новую Linux VM из конфигурации этого репозитория,
восстановить на ней существующую PrairieLearn и переключить учебный адрес.
Прежняя VM остаётся доступной для восстановления. Замена курса, пересчёт оценок
и обновление приложения не входят в инфраструктурный перенос.

## Основа и границы

Рабочее предположение — обычная Linux cloud image в QEMU/KVM VM Proxmox
с Docker Engine и Compose. Это не план размещения Docker в LXC. Конкретные
образ, VM ID, storage, bridge, CPU/RAM и диск выбираются после проверки
гипервизора и фиксируются обычной конфигурацией provisioning/inventory.
Состояние IaC, доступы и пользовательские данные остаются вне Git.

Deployment владеет общим Compose, конфигурацией Nginx, Task/Ansible и размещением
state. Platform предоставляет Community image и свой `compose/runtime.yml`;
курсы предоставляют готовые site/native. Новая VM не собирает Quarto, не получает
закрытые проверки и не создаёт новую регистрацию курса. Будущие exam-proxy,
exam-controller и файлы подготовки не являются условием этого переноса.
Обычный PL должен работать без них.

По read-only аудиту текущая установка находится в
`/var/lib/prairielearn/clean-20261107`, Compose project — `clean-course-20261107`.
Её Compose и Nginx происходят из исторического bundle, который не был tracked
в Git. Поэтому свежий Deployment нельзя считать побайтовым воспроизведением
текущей VM до переноса необходимых отличий и проверки итогового Compose.
Исторический bundle не копируется целиком как ещё один стек. Рабочие отличия
сопоставляются с текущими договорами и переносятся в принадлежащие Deployment
файлы; runtime/default image остаётся у Platform. Старые bind mounts исходного
кода также не заменяют опубликованный image без проверки их назначения.

В частности, базовый Compose Deployment включает собственную тестовую Moodle.
На VM используется внешний университетский Moodle: его не копируют,
не останавливают и не создают вместо него тестовую регистрацию. Для готовых
конфигураций и восстановленных данных уже есть самостоятельный
[steady runtime](runtime.md) — `compose.runtime.yml` без локальной Moodle, init и bootstrap.
Dev-preview с native dev-входом также не заменяет production Gateway/Bridge.

Проверенная граница runtime и оставшееся отличие действующей VM:

1. Новый entry принимает готовые PL/Bridge/Gateway configs и TLS на 443,
   требует существующие bind paths и проверяет `PG_VERSION` перед штатным
   запуском. Он не создаёт CA, аккаунты или initial grant. Resolved Compose
   проверен статически: только PL/Bridge/Gateway/Nginx; healthcheck обращается
   к собственному loopback ingress с прежней TLS identity, а не к старой VM.
   Это отделяет fixture provisioning от обычного старта, но ещё не подтверждает
   restore или воспроизведение всех live mounts и effective code.
2. Текущая VM получает готовые read-only каталоги course/catalog/materials;
   это не тот чистый native Git checkout, который требует `ansible/deploy.yml`
   вместе с `check-native-revision.mjs`. Новый runtime пока монтирует `/course`
   на запись и не подключает catalog/materials. Для первой репетиции выбирается точное
   восстановление текущей выдачи с выключенной публикацией: без нового export,
   implicit Git sync и смены native IDs. До запуска данных на новой VM явно
   согласуются mounts и единственный владелец последующей записи курса.
   Если следующим маршрутом выбирается native Git sync, отдельно проверяются
   checkout, native course path/commit и сохранение существующей регистрации;
   до этого существующий Ansible sync не применяется к восстановленному bind.
   Env/mount-only объединение не закрывает это различие договоров.

Работа разделена на четыре последовательных результата: согласованная
архитектура и необходимые изменения конфигурации; репетиция восстановления;
окончательная миграция данных при остановленных writers; переключение адреса
и приёмка учебного маршрута. Этот документ описывает порядок, но не объявляет
первые три результата уже выполненными. Новый универсальный orchestrator,
реестр версий, формат манифеста миграции и автоматическое слияние данных
не требуются: используются Compose, Git, Task/Ansible, штатные dumps и архивы.
При первой миграции сохраняются текущие application images; их дальнейшее
обновление проверяется отдельным изменением после принятого переноса.

## Подготовить новую VM отдельно

1. Проверить доступный storage и ресурсы гипервизора, текущие нагрузки и место
   для новой VM, резервной копии и временного восстановления. У действующей VM
   корневой диск 60 GiB, свободно около 6 GiB; это наблюдение, не запас для
   параллельного хранения всех копий. Размер нового диска выбирается по данным
   и запасу роста, без изменения старого диска ради самой миграции.
2. Создать новую VM с отдельным временным management IP и явной Linux/Docker
   конфигурацией. Не назначать ей одновременно учебный IP старой VM.
   Репозиторий, выбранный gitlink Platform и целевые overrides составляют
   воспроизводимую поставку. Секретные файлы подключаются извне.
3. Проверить итоговый Compose без подключения данных старой установки:
   адреса публикации, внутренние listeners, пути jobs/configs/state,
   UID/GID и отсутствие private файлов в публичной раздаче.
   Имена project/volumes и абсолютные пути новой VM задаются явно.
4. Подготовить те же опубликованные образы приложения, Gateway, grader
   и Workspace, что фактически используются на исходной VM. Default Gateway
   Deployment может отличаться от действующего: при переносе выбирается
   фактический digest, а не более старый default или mutable tag.
   Community, grader и Workspace image имеют разные роли.
5. Для Workspace создать отдельный Docker daemon и проверить его daemon ID.
   Native Workspace host получает только его socket и соответствующий jobs
   path. Сам PL и grader также проверяются по фактическим mounts; существующий
   системный daemon не назначается Workspace по удобству.

Проверяемый результат этого этапа — работающий изолированный контейнерный хост
и согласованная конфигурация. Он ещё не обслуживает исторический учебный курс.

## Что переносится

| Данные               | Что сохранить                                                                                                                                                                                                                 |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native PostgreSQL    | Полный логический dump: users, числовые course/instance IDs, permissions/enrollments, attempts, submissions, grades и история. После обновления 15 ноября сохраняются именно текущие баллы; повторный regrade не запускается. |
| Native course files  | Точные текущие каталоги, UUID и Git metadata; локальные изменения сначала сохраняются и разбираются. Инфраструктурный перенос не подменяет их новым экспортом.                                                                |
| `files`, `s3`, jobs  | Сохранённые ответы, вложения и Workspace work. Архивирование сохраняет hidden files, `.git`, `.pl-seed`, владельцев, режимы и относительные ссылки.                                                                           |
| Gateway              | Его SQLite/state и существующие registration/native mappings. Нельзя инициализировать новые DB вместо восстановленных.                                                                                                        |
| Private config и TLS | PL/Bridge/Gateway configs, service tokens, существующие server keys/certificates и публичные цепочки. Значения не печатаются и не входят в Git.                                                                               |
| Публичная выдача     | Принятый student site, материалы, public CA/JWKS и текущие ссылки на каталоги выпусков. Private checks туда не попадают.                                                                                                      |
| Развёртывание        | Несекретные параметры путей/адресов и список выбранных стандартных image identities. Пользовательские `.env`, dumps и state сохраняются отдельно.                                                                             |

Внутренние пути курса и привязки сверяются с исходной конфигурацией; новый host
path допустим, если контейнеры видят те же данные по согласованным путям.
Внешний Moodle остаётся прежним. Сохраняются issuer, clientId, deploymentId,
context/resource IDs и subjects, а также native `courseKey`/instance/IDs/UUID.
Email или похожее имя не заменяют эти связи.

## Пробное восстановление

В основу положен существующий [порядок backup/restore](local-operations.md).
Перед первой копией согласуется короткая остановка writers: новые входы,
native sync/regrade, grading jobs и Workspace. Готовность контейнеров не
подтверждает отсутствие записи. Workspaces останавливаются штатно, session
containers завершаются, сохраняется их работа. Затем корректно останавливаются
входные приложения и PL. Только после этой границы снимается сравниваемое
состояние и резервная копия.

Логический dump PL получают совместимыми `pg_dump`/`pg_restore` по фактическому
PostgreSQL major; текущая линия использует PG 17. При необходимости запускается
PG-only helper с исходным volume, без PL/cron/jobs и без внешней сети.
Не копируют работающий PG datadir как резервную копию. После завершения helper
архивируют обычные постоянные файлы. Защищённая копия располагается вне диска
исходной VM и проверяется штатными checksums и чтением dump.

На новой VM восстанавливаются новые пустые volumes/state; PostgreSQL — из dump
до запуска приложения. Порядок `initdb`, `volume-nocopy` и restore берётся из
локальной инструкции. Первый native bootstrap не должен создавать другой
administrator, пользователей или курсы поверх истории. Восстановленную копию
до проверки входа изолируют от внешнего Moodle и реальных пользователей.

Прежнюю VM можно снова запустить после согласованного завершения этой копии.
Тогда новая VM остаётся пробой: её данные уже отстают от рабочего источника.
Синтетические изменения пробы не переносятся обратно в production.

При проверке восстановления сравниваются:

- native IDs/UUID, пользователи, роли, сохранённые ответы и текущие оценки;
- чтение прежней сдачи через преподавательский интерфейс и ссылки файлов;
- Workspace HEAD, branches, index, staged/unstaged/untracked files и Git objects;
- Save, Stop/Resume и новая синтетическая сдача на изолированной копии;
- повторный запуск с теми же state/project без новых IDs и сброса файлов;
- точный student site и доступность материалов при закрытых private routes.

Оригинальный HTTPS origin сохраняется. Временный IP не подставляют молча в LTI
registration и не отключают TLS verification. Проверка полного исходного origin
до переключения возможна только в отдельно подготовленном маршруте клиента,
который не создаёт конфликт IP и не направляет настоящих студентов на копию.
Если такого маршрута нет, реальный Moodle→PL путь проверяется в окне переключения.

## Окончательная копия и переключение

После успешной репетиции назначается окно без учебной записи. Сохраняется
действующая резервная копия и доступ к старой VM через management-консоль.
Проверяется маршрут возврата прежнего адреса. На старой VM снова закрываются
входы, завершаются jobs/Workspace и останавливаются writers. Снимаются **новый
полный DB dump** и окончательная копия постоянных файлов после этой границы.
Не вводится собственный протокол DB-delta или слияния двух историй. Для большого
файлового дерева допустима предварительная обычная копия и финальная сверенная
досылка при остановленных writers; DB всегда восстанавливается согласованно.

Пробные данные новой VM заменяются именно этой финальной копией; после restore
повторяется сравнение IDs, оценок и файлов. На старой VM приложения остаются
остановленными. Учебный адрес переключается на новую VM: для нынешнего literal
IP это передача адреса/маршрута после отключения старого интерфейса от него,
а не DNS-переименование. Одновременная публикация двух writers запрещена.
Прежние TLS identity, ключи и LTI origins сохраняются.

До открытия входа студентам проверяются HTTPS, свежие подписанные Moodle
launches, Student/Teacher права, прежние submissions/grades, Workspace resume
и новая контролируемая сдача. Проверяется, что старые jobs не исполняются вторично.
Успех утверждается по учебному маршруту и данным, а не только `compose up --wait`.
Exam-компоненты остаются выключенными и не влияют на эту приёмку.

## Граница возврата

Пока на новой VM нет новых пользовательских изменений, можно остановить её
writers, вернуть учебный адрес старой VM и запустить прежнюю сохранённую
установку. Сначала исключают два активных IP и два писателя. Само наличие старой
VM не возвращает браузеры автоматически; оператор проверяет адрес и доступ.

После новых сдач, оценок, изменения прав или Workspace на новой VM простое
включение старой потеряет эти изменения. Такая ситуация требует нового окна
остановки и согласованного обратного переноса актуальных DB/files/state либо
исправления новой VM. Откат без потери новых записей заранее не обещается.
Старую VM, её диски и резервные копии сохраняют до отдельного решения владельца;
общий prune, удаление volumes и уничтожение старой установки в этот план не входят.

## Что ещё предстоит реализовать и подтвердить

Steady runtime без test Moodle и fixture init/bootstrap уже доступен; до
переключения требуется конкретная конфигурация новой VM и следующие сверки:

- Сохранить read-only generated course paths/UUID и необходимые catalog bindings;
  определить единственного владельца записи, не применять Git-sync к прежним bind.
- Сравнить действующие bridge/tools bind bytes с точным image и принять нужный
  effective code; проверить соседние файлы, на которые ссылается native PL config.
  Совпадающее перекрытие удалить, нужные отличия закрепить явно с их владельцем,
  сохраняя текущую реализацию для первого переноса.
- Подключить прежние public JWKS и student materials с теми же URLs и правами:
  собственный TLS healthcheck не заменяет раздачу `/public` и `/materials`.
- Согласовать Workspace host для runtime с отдельным daemon, прежними jobs,
  session images и UID/GID; подтвердить Git и Save/Stop/Resume. Существующий
  fixture Workspace override пока не является таким вариантом.
- Проверить гипервизор и ресурсы новой VM, доступность точных application/grader/
  Workspace image bytes, пути и владельцев данных; затем выполнить описанные выше
  репетицию restore, финальную копию при остановленных writers и приёмку до входа
  студентов. Локальный image ID не считается гарантированным registry RepoDigest.

Оставшиеся site-настройки оформляются стандартным Compose override после сверки
и проходят отдельную приёмку.
Существующий `ansible/deploy.yml` доставляет готовые site/native в уже работающий
PL по native Git договору; он не создаёт VM и не выполняет этот перенос БД.
Будущий exam-controller ещё отсутствует; его реализация и проверка Windows
идут отдельно от инфраструктурного переезда.
