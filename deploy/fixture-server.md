# Отдельный серверный пилот Moodle и PrairieLearn

На выделенной Linux VM `10.135.250.231` запускаются два проекта Compose.
Экзаменационный публикует Squid на `21680/tcp`. Тестовые Moodle и PrairieLearn
доступны через него по своим HTTPS-именам. Обычный контроль публикует Nginx
на `21645/tcp` и `21646/tcp`. У обоих проектов свои базы, Native-курсы, домены
HTTPS, каталоги и ключи. Gateway, Bridge и базы обоих проектов остаются в
сетях Compose. Контроллер exam-lab и Wazuh настраиваются своими средствами.

## Входы двух проектов

Установите Docker Engine, Compose с поддержкой `!reset`, OpenSSL и `go-task`.
Инициализируйте закреплённую Platform командой `git submodule update --init`.
Подготовьте опубликованные Native-наборы Java «Числовые вычисления» для
экзамена и «Управление обработкой данных» для обычного контроля. Для каждого
подготовьте чистый Git checkout и его реестр `pl-courses-v2`, как в
[локальной инструкции](fixture-local.md). Образы Moodle, Squid и Gateway
берутся той же сборкой. Для экзамена нужен Gateway с `examAudit`.

Создайте два пустых закрытых каталога с правами `0700`, принадлежащих
оператору Docker. В отдельных приватных env-файлах укажите входы из
[локальной инструкции](fixture-local.md) с новыми `COMPOSE_PROJECT_NAME`,
`FIXTURE_DIR`, `FIXTURE_NATIVE_DIR` и `FIXTURE_REGISTRY`. В оба файла добавьте
явный выбор серверной публикации.

```dotenv
FIXTURE_SCOPE=server
FIXTURE_SERVER_IP=10.135.250.231
```

В файле обычного проекта используйте отдельные имена и порты.

```dotenv
COMPOSE_PROJECT_NAME=ordinary-fixture-server
PL_HOST=pl.ordinary-server-20261119.test
PL_HTTPS_PORT=21646
MOODLE_HOST=moodle.ordinary-server-20261119.test
MOODLE_HTTPS_PORT=21645
```

Для экзамена предназначены другие origin и отдельная свободная подсеть
Docker вне `10.0.0.0/8`. Проверьте, что default bridge каждого проекта и
экзаменационная ingress-сеть также находятся вне клиентской сети.

```dotenv
COMPOSE_PROJECT_NAME=exam-fixture-server
PL_HOST=pl.exam-server-20261119.test
PL_HTTPS_PORT=21644
MOODLE_HOST=moodle.exam-server-20261119.test
MOODLE_HTTPS_PORT=21643
EXAM_ID=exam-lab-server-pilot
EXAM_INGRESS_SUBNET=172.16.252.0/29
EXAM_PROXY_PUBLISH_PORT=21680
```

При первом старте состояние закрепляет адрес публикации за проектом.
Для повторов используйте те же файлы и пути. По умолчанию команды работают
в локальном режиме и подходят для прежних каталогов состояния.

## Сетевой вход и запуск

В выделенной VM настройте клиентский доступ в существующей таблице nftables
`inet exam_ingress`. Проверка источника должна срабатывать до Docker DNAT
для клиентских портов Docker и в фильтре `input` для служб на самой VM.
Для `10.135.250.231` разрешите из `10.0.0.0/8` только HTTPS обычного контроля,
Squid, HTTPS опроса контроллера `21650/tcp` и события Wazuh `1514/tcp`.
Оставьте правило административного SSH с адреса бастиона. Проверьте новую
конфигурацию `nft --check --file /etc/nftables.conf` и загрузите её штатным
`systemctl reload nftables`. Проверяйте таблицу командой
`nft list table inet exam_ingress`.

Регистрацию Wazuh, доступ преподавателя или оператора к административным
интерфейсам, конфигурации и выдачу ключей ведите по отдельному
административному каналу.

```sh
go-task fixture:up FIXTURE=ordinary FIXTURE_ENV=/private/ordinary-server.env
go-task fixture:up FIXTURE=exam FIXTURE_ENV=/private/exam-server.env
go-task fixture:status FIXTURE=exam FIXTURE_ENV=/private/exam-server.env
```

Squid проверяет фактический адрес TCP-клиента и записывает его в закрытый
журнал. Gateway получает тот же адрес через один доверенный Squid и проверяет
сеть `10.0.0.0/8` при запуске работы. Если Docker или маршрутизатор подставляет
адрес вне `10.0.0.0/8`, запрос получает отказ. Если маршрутизатор подставляет
общий адрес внутри `10.0.0.0/8`, сначала исправьте маршрут и проверьте адрес
снова. Для подтверждения конкретного ПК дополнительно нужна проверка его
регистрации контроллером. Обычный Nginx проверяет адрес TCP-клиента отдельно.

## HTTPS контроллера

Поднимите backend контроллера exam-lab на `127.0.0.1:21651` со своим файлом
состояния и отдельной регистрацией каждого ПК. Подготовьте новый закрытый
каталог TLS, принадлежащий оператору Nginx. Сценарий выпустит сертификат с
IP SAN `10.135.250.231` и закрепит за каталогом адрес сервера. Nginx принимает
только `POST /exam/v1/poll` от клиентов `10.0.0.0/8`. Действия преподавателя
выполняются через административный канал контроллера.

```sh
install -d -m 700 /private/controller-server
bash scripts/exam-controller-tls.sh /private/controller-server --server 10.135.250.231
nginx -t -p /private/controller-server/ -c nginx.conf
nginx -p /private/controller-server/ -c nginx.conf
```

Для перевыпуска сертификата запустите тот же сценарий с `--renew`, проверьте
конфиг и перезагрузите Nginx. Закрытый ключ сервера и CA сохраняются, серийный
номер сертификата сервера меняется. Сравните отпечаток опубликованного
`controller-ca.cer` до и после перевыпуска и проверьте Windows-опрос с тем же
доверием. Обычное повторение команды сохраняет текущий сертификат.

```sh
bash scripts/exam-controller-tls.sh /private/controller-server --server 10.135.250.231 --renew
nginx -t -p /private/controller-server/ -c nginx.conf
nginx -s reload -p /private/controller-server/ -c nginx.conf
```

## Доверие и проверки

Обычный клиент разрешает оба имени своего проекта в `10.135.250.231` и
проверяет публичный CA именно этого проекта (`state/tls/ca.crt`). Экзаменационный
клиент подключается к `http://10.135.250.231:21680` как к forward proxy и
доверяет выпущенному этим проектом публичному `squid-ca.cer` или `squid-ca.pem`.
В Squid настроено внутреннее разрешение двух экзаменационных имён. Передавайте
Windows публичные CA контроллера и Squid через административный комплект
с ожидаемыми отпечатками SHA-256. Закрытые ключи сохраняются на сервере.

Проверяйте с двух выделенных узлов. С разрешённого узла подтвердите исходный
IP в закрытом журнале Squid, HTTPS через Squid с проверкой CA, вход в обычный
проект, Moodle LTI и сдачу в экзаменационном проекте. Из маршрутизируемого
узла вне `10.0.0.0/8` соединения с опубликованными клиентскими портами должны
блокироваться. Проверьте закрытие прямых адресов экзаменационного Moodle и PL,
Bridge, Gateway, обеих баз и административных сервисов. Самопроверка Nginx
внутри контейнера подтверждает готовность процесса. Проверка маршрутизации
выполняется отдельным запросом с клиентского узла.

Контролируйте состояние обоих проектов командой `fixture:status` с их
входами. Повтор `fixture:up`, перезапуск VM и `fixture:down` с исходным
файлом сохраняют тома и ключи. В проверке повторного запуска сравните
регистрации, fingerprint CA, Native ID и результат сохранённой сдачи.
